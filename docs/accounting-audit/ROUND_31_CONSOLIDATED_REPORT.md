### 1.2 قواعد الأدلة المطبَّقة (ثابتة عبر الجولات)
1. لكل شاشة إنشاء/اعتماد: إدخال كامل → صورة حقيقية **قبل** زر الحفظ/الاعتماد → النقر → دليل بعدي (رد API + لقطة DB) → ربط بالقيود والتقارير ورقم الاختبار.
2. رسالة النجاح ليست دليلاً: كل عملية تُطابَق على UI/DB/المخزون/الأستاذ/الخزينة/الأطراف/التقارير.
3. التوقعات تُحسب **قبل** التنفيذ وتُكتب في `TEST_DATA.md`/`FINANCIAL_RECONCILIATION.md`؛ الفرق يُوثَّق بعيب أو بقرار سياسة.
4. لا إصلاح كود، لا إضافة حسابات أو قيود تسوية لجعل المطابقات تنجح؛ لا تغيير إعدادات أساسية إلا موثَّقاً (مثل تفعيل محاكاة المزوّدين في R30 وتسجيله في `TEST_DATA.md`).
5. التمييز الصريح بين **مؤكَّد** (مع دليل)، **مشتبه** (بلا دليل كافٍ)، و**قرار سياسة** (سلوك مقصود يحتاج موقفاً من المالك).

## 6. خطة إعادة الاختبار بعد الإصلاح

### 6.1 المبدأ
لكل جذر (§4.4) حزمة إعادة اختبار جاهزة: **رنر + فاحص + لقطات مرجعية** موجودة في `scripts/` و`evidence/`. إعادة الاختبار تُجرى على مستأجر معزول جديد ببذرة معروفة (وصفة إعادة البناء في `CONTINUITY_R24.md` §3)، ويُعاد تشغيل الفاحص؛ معيار الإغلاق: **كل التحققات المرمَّزة بمعرّف العيب تمرّ**، ولا تحقق كان يمرّ صار يفشل (انحدار).

### 6.3 اختبارات انحدار عرضية (تُجرى بعد كل حزمة)
1. **مطابقة الفرعي/الرقابة** الشاملة (صندوق، بنك، ذمم مدينة/دائنة، مخزون، ضريبة) — `round30-check.py` §G أو تقرير MF-33 حين يُبنى.
2. **القوائم**: ميزان متوازن، الميزانية = الأصول − الالتزامات − حقوق الملكية بلا سطر محسوب (بعد MF-04)، قائمة الدخل = Σ حسابات الدخل.
3. **الإقرار الضريبي** = حسابات الضريبة للفترة.
4. **إعادة تشغيل كل الفاحصات R10–R30** على بذرة واحدة موحَّدة (يتطلب دمج الرنرات — مقترح كـR32 بعد أول حزمة إصلاح).

### 6.4 ما يحتاج بيئة متصلة (لا يمكن إعادة اختباره محلياً)
ZATCA sandbox (MF-19)، ميسر/جيديا/NeoLeap الحقيقية، Salla، OCR، واتساب/بريد، التوقيع الإلكتروني — تحتاج تفويضاً وبيانات منشأة اختبار (`MISSING_FEATURES.md` §6 القرار 12).
